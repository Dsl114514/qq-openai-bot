# 接入 OpenAI 兼容接口：一个抽象层，和一个修不了的架构限制

## 为什么加这个

机器人原本硬绑在 DeepSeek 网页版上：每条消息都要先解一次算力挑战，而且 `userToken` 会**不可预测地失效**。任何有普通 API Key 的人 —— OpenAI、DeepSeek 自己的付费接口、Groq、本地 llama.cpp —— 都应该能直接指过来，跳过这整套东西。

## 抽象放在哪一层：`complete()` 是唯一的缝

所有调用方（QQ webhook、`/v1`、定时任务、工作台）都问同一句话："这段提示词怎么答"。以前答案只有一个来源，于是 **DeepSeek 特有的概念（算力挑战、会话 ID、一次性解）渗进了每一个调用点**。

OpenAI 兼容接口**完全不需要**这些：就是一个带鉴权的 POST。所以 provider 的选择必须在**这些调用点之下**，否则每个调用点都要长出 `if (deepseek)` 分支，而这些分支必须互相保持同步。

### 一个关键的不对称

| | DeepSeek 网页版 | OpenAI 兼容 |
|---|---|---|
| 算力挑战 | 每条消息解一次 | 不存在 |
| 会话延续 | 需要 session id + 父消息 id | 每次重发完整历史 |
| 降级阶梯 | 需要（会话会被污染） | **有害**（见下） |
| 令牌失效 | 随时 | 不会 |

**这个不对称正是为什么它是分发器而不是共享管线** —— 共享阶梯等于对一个不可能受益的端点反复重试。

## 实测踩到的 bug：降级阶梯在打第三方

错误信息是"模型返回了空回复"，但用户自己的 API 日志显示 **`HTTP 429 error code: 1015`**。

根因：`completeWithDegradation` 的三阶段阶梯**还在跑**。我在 `complete.ts` 的注释里写了"外部 provider 不需要阶梯"，**却忘了 QQ 的调用路径仍然裹着它**。后果是：

> **每条用户消息最多发 3 次请求**，而每次重试都在加剧限流。

修法：外部 provider **只发一次**。真正的失败如实报告 —— 阶梯的补救动作（丢父指针、开新会话）在没有"会话"这个概念时毫无意义。

**同时修了误导性的错误文案**：原来无论什么原因都说"模型返回了空回复（已依次尝试：沿用会话 → 去掉上下文 → 开新会话）"，而现在外部 provider 根本没有阶梯。改成把上游错误原文带出来。

## 第二个实测 bug：日志说错了 provider

审计行记的是 `model=deepseek-web`，而请求**实际发到了用户的 `agnes-2.5-flash`** —— 因为日志记的是请求里的 `model` 字段，而那是每个作用域都带的默认值。

> 排查"我的 API 为什么没反应"时，第一条线索指向了 DeepSeek，**方向完全错了**。

现在记**解析后的**模型名，并在非 DeepSeek 时加上 provider 前缀，同时把 provider 和实际模型写进 request_body。

## 第三个实测 bug：空 Base URL 被静默忽略

表单里清空 Base URL 后保存，返回"保存成功"，但旧 URL **仍然生效** —— 因为 `normalizeProvider` 把空字符串当作"未提供"而回退到旧值。那对于部分更新是对的，但在这里等于**"保存了，什么也没变"**。

现在显式拒绝：使用 OpenAI 兼容接口时 Base URL 不能为空。

## API Key 的存放：和配置分开

```
provider:config   → kind / baseUrl / model / timeoutMs   （非机密）
provider:apiKey   → 只有 Key                              （机密）
```

**这个分离是有意的**：它让"永远不把 Key 返回给客户端"成为**存储布局的属性**，而不是一条需要人记住的规则 —— 任何序列化 config 的代码都不可能带上 Key，因为它不在那个对象里。

接口返回的是 **SHA-256 前 8 位的指纹**加来源标签（`D1` 或 `Worker secret`）。不是为了好看：有两把 Key 的人需要知道装的是哪一把，而唯一安全的回答方式是哈希。实测确认响应里没有 `apiKey` 字段、也不含原文。

## 一个修不了的架构限制（本文件最重要的部分）

用户接入了自己的中转 API，机器人一直返回空回复。实测对照：

```
本机  → apihub.agnes-ai.com : HTTP 200（6 种请求头变体全部成功）
本机  → 无效 Key             : HTTP 401 Invalid token（服务正常，按 Key 判断）
Worker → 同一个 URL          : HTTP 429 error code 1015（持续数分钟）
Worker → 无效 Key            : 同样是 429，不是 401
```

**最后一行是决定性的**：连无效 Key 都拿不到 401，说明拦截发生在**请求到达该服务之前**。

`error code: 1015` 是 **Cloudflare 自己的限流**。触发条件不是请求形态（6 种 User-Agent 变体、加 `origin`/`referer`/`x-requested-with` 全部 200），也不是 Key（换 Key 无效），所以只能是**来源 IP**。

**这是 Cloudflare Worker 的固有限制**：Worker 从 Cloudflare 自己的网络出口出去，访问另一个 Cloudflare 后面的服务时，很容易命中针对该来源的风控规则。**Worker 无法更换出口 IP**，所以代码层面无解。

### 对操作者的实际含义

- 中转/聚合类服务如果对 Cloudflare 出口有风控，Worker 就用不了；
- 直连官方 API（`api.openai.com`、`api.deepseek.com`）通常没问题；
- 需要中转时，找一个不限制 Cloudflare 出口的，或把请求转发到自己控制的机器。

**因此 429 的错误文案区分两种可能**："一次性突发限制 → 稍后重试"与"持续出现 → 来源被挡，重试无用，需换接口或换出口"。把持续性的来源拦截说成"限流请重试"，会让人白等很久 —— 这正是我一开始差点得出的结论。

## 已考虑并否决

- **把 Key 存在配置对象里**：序列化 config 的任何代码路径都会带上它，而"记得过滤"是会失效的规则。
- **外部 provider 也跑降级阶梯**：会变成 3 倍计费请求，而且拦住我们的正是它（实测）。
- **把 429 一律当限流重试**：见上 —— 持续性的来源拦截会被误诊成临时限流。
- **用模型名 `deepseek-web` 直通外部接口**：那是个必然 404，而且看起来像 Key 坏了，所以它被当作"无覆盖"处理。
- **保留仓库里的真实 D1 id 和域名**：改为占位符模板，真实值放 gitignore 的 `wrangler.local.toml`，用 `npm run deploy:local` 部署。
