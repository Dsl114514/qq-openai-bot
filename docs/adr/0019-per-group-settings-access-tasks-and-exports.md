# 按群设置、黑白名单、定时任务、导出与统计

这一批加了八项能力。下面记的是**为什么这样设计**，以及过程中实测发现的三个真实问题。

## 一、设置为什么存「部分覆盖」而不是完整快照

一次回复的模式由三层决定，**上层赢**：

1. 消息里的指令（`/think`、`/search`、`/fast`）
2. 该群的覆盖值
3. 全局默认

关键在于**第 2 层存的是「这个群与全局不同的地方」**，而不是一份完整设置。

如果存完整快照：某个群第一次被编辑的那一刻，全局默认就被**冻结**进这个群了。之后你把全局的深度思考打开，**这个群永远不会跟上** —— 而界面上看不出任何异常，它只是「没有生效」。

> 所以 `resolveSettings` 是**合并**而不是替换，`undefined`（继承）和 `false`（明确关闭）是两种不同的状态。

**这也是为什么按群的表单用三态下拉而不是复选框。** 复选框只能表达「开/关」，表达不了「未设置」—— 而把「未设置」折叠成「关」，就会在第一次编辑某个群时静默覆盖掉全局设置。

### 实测

```
全局 thinking=true
  → A 群存覆盖 thinking=false
  → A 群生效值 = false（覆盖生效）
  → 全局仍然是 true（证明是覆盖在决定）
  → 清除 A 群覆盖 → 生效值回到 true（继承恢复）
```

## 二、黑白名单：为什么不是「一个列表 + 模式开关」

两个不同的问题被问出来：

- **「这是私有机器人吗？」** —— 只有名单上的 id 能用。这是**白名单**，而它**必须默认拒绝**，否则它根本不是限制。
- **「把机器人挡在这些地方之外」** —— 除了名单上的，都能用。这是**黑名单**。

把它们塞进「一个列表 + allow/deny 开关」就**无法同时使用**，而同时使用恰恰是最常见的需求：「私有机器人，但有一个信任的群可以随便用」。

所以模型是**每种对象各一个白名单和一个黑名单**，`mode` 决定名单之外的 id 得到什么。

### 两条不可动摇的规则

**1. 黑名单永远优先。** 两边都有的 id 会被拒绝。这是唯一让「拉黑」有意义的读法 —— 反过来，一个过期的白名单条目会悄悄重新启用你**特意封掉**的东西。

**2. 默认是开放的。** 权限变更的默认方向应该是「不减少现有能力」。升级后突然所有人都不能用了，排查起来会以为是坏了。

**3. 私聊不受群白名单限制。** 私聊没有群，用群名单去卡它会把所有私聊都拒掉 —— 那从来不是操作者的意思。

### 被拒绝时说什么

**什么都不说。** 不回复、也不告诉对方原因 —— 告诉对方「你被拉黑了」等于告诉他去换一个号，等于给他一个可以尝试的目标。但**记进审计台**，因为你需要能核对它是否按预期工作。

## 三、定时任务：把「发牢骚」推广，而不是并列

原来的「发牢骚」只能表达一种形状：每天 N 次、随机时间或一个固定时间、固定文本或模型生成。

`src/qq/tasks.ts` **能表达上面全部**，外加：每周、按间隔、一天多个不同时刻、每个任务各自选固定或生成。所以旧形状是新能力的**子集**，不是一个并行的第二套系统。

### 旧配置是迁移，不是忽略

旧行是「有人配过这个功能」的唯一记录。丢掉它 = 静默停止一个别人设置好的定时消息，而症状看起来就是「功能坏了」—— 正是本项目反复修的那类问题（见 [ADR-0015](0015-group-id-must-be-selected-not-pasted.md)）。

实测迁移结果：

```
旧配置 {enabled:true, perDay:1, mode:"random", text:"冒泡"}
  → 新任务 kind=interval, everyMinutes=1440, content={kind:"fixed", text:"冒泡"}
旧配置保留在数据库里，可回退
```

**幂等**：重复执行不会产生重复任务。也**提供手动按钮** —— 自动迁移发生在下一条消息到达时，安静期可能等很久，操作者看到空列表无从判断是没迁移还是没实现。

### 但迁移**每次事件都会跑**，所以它必须先比较再写

这是实测踩到的**最严重的一个 bug**，而且是部署后才由真实数据暴露的。

第一版无条件调用 `saveTask`。而调度器在**每一条到达的消息**上都会先跑一次迁移，于是：

> 你在控制台把任务内容改掉 → **下一条群消息到达时就被旧配置的值覆盖回去** → 日志里没有任何痕迹。

**实测证据**（生产数据）：

```
旧配置（迁移读取）: @核巨啸 你好呀wzc小朋友
任务（调度发送）  : lxy 神了              ← 操作者的编辑
指纹标记          : 匹配旧配置
```

连续 **12 次**迁移调用后，任务保持 `lxy 神了` 不变。修复前，第一次调用就会把它覆盖。

**修法**：迁移记录它转换的那份配置的**指纹**，只有指纹变化时才写任务。这给出了操作者预期的语义：

| 你改的是 | 结果 |
|---|---|
| 控制台里的**任务** | 旧配置没变 → 指纹没变 → **不覆盖** |
| **旧配置**本身 | 指纹变了 → 任务同步更新 |

**指纹必须用规范化序列化。** 第一版用 `JSON.stringify(parsed)`，而 `JSON.parse` **保留源文本的键序**，所以同一份配置换个键序写就变成「变了」，会触发一次不必要的覆盖。测试直接抓到了这一点（我原先的注释还声称它不会）。现在按键排序后再比较，数组保持顺序。

> 这条经验比这个 bug 本身更重要：**「幂等」不等于「无害」**。重复执行不产生重复行，但它每次都在写，而写入会抹掉别人的修改。真正需要的是**先比较再写**。

### 时间到了但没人说话怎么办

调度沿用既有做法：**没有定时器，而是在任何消息到达时检查**。免费版 Worker 的 cron 调用和普通请求拿一样的 10 ms CPU 预算，而一次发送需要解题加模型调用（[ADR-0007](0007-qq-bot-solves-its-own-pow.md)）。

**后果必须说清楚，所以界面上写明了**：群里完全没人说话时任务不会准时触发，会在下一条消息到达时补上。

**触发窗口是「已过点」而不是「正好这一分钟」** —— 因为 Worker 只在事件到达时运行，要求精确匹配分钟会在那个分钟恰好没人说话时**整个错过**。

### 每次只跑一个任务，且只在成功后记账

- **一次调用只发一条**：多条会在同一次调用里突发消耗被动回复配额。
- **发送成功后才写「已运行」**：失败时下一条消息会重试。反过来（先记账）会把失败的消息**永久丢掉**。
- **手动「立刻运行」不占用当天额度** —— 否则 09:00 测试一下就会让 21:00 的真正发送被跳过。

## 四、导出：为什么流式，以及为什么 CSV 不能简单拼逗号

记录行里有**任意文本**（正文是模型输出，含引号、逗号、换行）。

- **流式输出**：一个月的调用比 Worker 应该一次性持有的字节多得多，而且拼字符串会吃掉 10 ms CPU 预算。分页读取、边读边写，内存基本恒定。
- **CSV 正确转义**：只在需要时加引号（含分隔符、引号或换行时），这样数字列在表格里仍然是数字、能求和。
- **导出带上当前筛选**，所以「导出」=「导出我正在看的这些」。

### 实测发现的 D1 硬限制

导出第一次跑就失败了，而**错误被写进了输出文件本身**：

```
# ERROR: D1_ERROR: variable number must be between ?1 and ?100
```

**D1 每条语句最多 100 个绑定参数**，而我按 200 行分页，`IN (?1…?200)` 直接超限。

这个 bug 之所以能一眼定位，是因为**流中途出错时把错误写进了产物**，而不是返回一个静默截断的文件 —— 后者与「这个范围内记录比较少」无法区分。

现在分页 50 行，并且在绑定前**显式断言**上限，让失败信息说明是哪个限制，而不是转述 D1 的原始报错。

修复后实测：**158 行、12 个字段全部对齐，正文经转义后仍能反解为 JSON。**

## 五、统计：分桶必须用本地日

`created_at / 86400000` 会按 **UTC** 分桶，于是 Asia/Shanghai 每天 0 点到 8 点的调用全部落到**前一天**。

> 一个每天有三分之一时间是错的图表，比没有图表更糟。

所以按配置时区偏移分桶（从 `Intl` 取，DST 边界内最多影响一小时，可接受）。实测：当天的调用出现在当天。

**聚合在 SQL 里做，不在 Worker 里。** 把几千行拉进 Worker 用 JavaScript 求和，是在用那 10 ms CPU 预算做数据库免费就能做的事。

## 六、过程中修掉的三个真实问题

### 1. `zonedNow` 对非法时区会抛异常

它**每次事件都会调用**。一个拼错的 `QQ_SESSION_TZ` 会同时打挂调度器和回复路径 —— 配置失误变成全面故障。现在回退 UTC 并记录：调度偏几小时是可恢复的，不回复不是。

### 2. 逗号分隔的时间被当成一个 token

`times=09:00, 21:30` 是 API 调用方最自然的写法，但服务端当成单个字符串，于是报「至少需要一个有效时间（HH:MM）」—— **一条没有透露「值从未被拆分」的错误信息**。

现在接受逗号、全角逗号、分号和空白作为分隔符。测试**直接调用真实的 `splitList`**，而不是它的副本 —— 副本会漂移，而基于副本的测试会在真实代码改变后继续通过。

### 3. 未知 API 路径返回 HTML 外壳和 200

因为 `/admin/*` 的兜底路由排在后面前面。客户端于是死在 `JSON.parse` 上，报「意外的 `<`」，既没提路径也没提原因；而 **200 让任何监控都看不见**。

现在 `/admin/api/*` 有独立的 JSON 404，并登记在原位（API 路由之后、外壳兜底之前）。路由顺序在这个项目里已经踩过一次，注释里写明了原因。

## 已考虑并否决

- **按群设置存完整快照**：会在首次编辑时冻结全局默认，之后全局改动静默不生效。
- **按群设置用复选框**：表达不了「继承」这个第三态，会把未设置折叠成关闭。
- **白名单/黑名单合一个列表 + 模式开关**：无法同时使用，而「私有机器的例外群」是常见需求。
- **被拒时回复原因**：等于告诉对方怎么绕过。
- **定时任务写 cron 表达式**：界面上可读性差，且解析器与显示可能不一致 —— 所以接受 cron 输入但**展开成时间列表存储**。
- **导出时用 `content-disposition: attachment` 以外的方式**：浏览器会尝试渲染 JSON。
- **统计在前端聚合**：要把全部行发到浏览器，还让同一逻辑存在两份。
