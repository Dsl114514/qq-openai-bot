# 分块 PoW 必须用自研 JS 实现，不能用官方 wasm 模块

DeepSeek 的算力挑战按本机实测约需 350 ms 单线程计算（19.8 µs/hash × 难度 144,000 的期望值），而 Cloudflare Workers 免费版每次调用只有 **10 ms CPU**（Cron Trigger、Durable Object alarm、Queues consumer 也一样只有 10 ms——wall time 有 15 分钟，但 CPU 不累积）。唯一不花钱的出路是把 `[0, difficulty)` 切成若干升序区间，每段单独一次调用。

> **部署后修正**：Cloudflare 的 isolate 比本机快约 300 倍（实测约 67 ns/hash），CPU 天花板约 15 万次哈希，所以一次挑战实际只需**几次**调用，而非下面估算的 100–200 次。另外，"按测得速度决定分块大小"这个计划**已经作废**——部署环境的时钟全部不可用。见 [ADR-0005](0005-no-clock-on-workers-free.md)。分块本身仍然必要，只是尺寸靠探测而非计算。

官方模块**技术上完全可以在 Worker 里跑**——零 import、无 WASI、无共享内存、无线程、无 atomics，`WebAssembly.instantiate(bytes, {})` 直接成功。但它导出的入口是：

```
wasm_solve(retptr, challenge_ptr, challenge_len, prefix_ptr, prefix_len, difficulty)
```

**六个参数里没有起始 nonce。** 它永远从 0 开始扫。所以第 k 段调用仍然要重算前 k−1 段的工作，总工作量退化成 O(K²) 而不是 O(K)——分块彻底失效。

因此必须在 TypeScript 里重写 Keccak-23，让搜索区间成为函数参数。

## 后果

- 我们承担了一份**算法副本的维护责任**。它已经被官方 wasm 交叉验证（参数扫描从 64 个候选编码中筛出唯一解，且官方模块能复现我们铸造的 nonce），但上游随时可能改算法。
- **测试套件是这件事的一部分，不是附属品。** 开发过程中出现过五个"看起来完全正确"的实现缺陷：RC[11] 手抄错一个半字节、π 置换源索引写反、目标字 hi/lo 配对颠倒、`0x06` 落到错误的半字、动态字被二次异或。每一个都产出貌似合理的摘要，且**每一个都只被"官方 wasm 当裁判 + 分块等价性断言"抓出来**。纯摘要相等测试连其中至少一个都抓不到（源索引写反能通过摘要测试）。
- 官方 wasm 仍然打包在仓库里，但**只用于测试**，不参与生产路径。

## 已考虑并否决的方案

- **Workers Paid（$5/月）**：CPU 上限从 10 ms 变成 5 分钟，一次调用即可算完，代码简单得多。被否决是因为"不能有月费"被明确声明为不可协商约束。
- **外部 sidecar 算 PoW**：被否决是因为"不接受任何外部机器"同样不可协商。
- **依赖 rollover CPU**：Cloudflare 文档承认存在未公开的 CPU 借用池，有第三方观测到 227 ms CPU 的请求正常完成。**不作为设计依据**——池子大小与重置策略均未公开，且文档明确说"持续超额会被终止"。可以作为将来的优化项另行验证，但不构成架构。
- **额外购买云服务器**：同 sidecar，被否决。
