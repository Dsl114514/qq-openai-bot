# 算力挑战解是一次性的，缓存复用会导致静默的空回复

这是一个**由"优化"引入的 bug**，而且它的失败方式几乎不可见 —— 值得完整记下来，因为它说明了一类优化为什么危险。

## 现象

QQ bot 接入后，用户发消息得到：

```
出错了：the model returned an empty reply
```

审计日志里的模式非常明确：

| id | 内容 | completion_tokens | deepseek_message_id | 结果 |
|---|---|---|---|---|
| 49 | `hi` | 8 | `2` | ✅ 正常回复 |
| 51 | `你是谁` | 1 | `null` | ❌ 空 |
| 53 | `you name` | 1 | `null` | ❌ 空 |
| 55 | `hi` | 1 | `null` | ❌ 空 |

**第一条成功，之后全空。** 而且每一条的 HTTP 状态都是 **200**，发送也是 `ok: true` —— 从日志表面看一切正常。

## 根因

原先为了省 CPU，把解好的 `x-ds-pow-response` 存进 D1，后续消息复用它。当时认为挑战有效期 300 秒，复用是免费的。

**这个前提是错的。** 直接对线上上游做了对照实验 —— 同一个解连续发两次：

```
use #1: HTTP 200  content="Hello"   ✅
use #2: HTTP 200  content=""        ❌
```

**解是一次性的。** 而第二次请求**不被拒绝**，它返回 200 加一个空答案。这就是为什么这个 bug 如此难发现：

- 状态码是 200，不是 4xx；
- 消息发送成功（`ok: true`）；
- `completion_tokens` 是 1 而不是 0，看起来像"模型说了个很短的词"；
- 唯一的线索是内容为空，而这在日志里要展开响应体才看得到。

一个"省 CPU"的优化，把服务变成了从第二条消息起全部回答空内容，而所有监控指标都是绿的。

**修复**：`obtainPowHeader` 不再读写缓存，**每条消息都重新求解**。一次求解约 1–2 秒，完全负担得起 —— 当初引入缓存的那个"350 ms 太贵"的估算本身就是错的（见 [ADR-0007](0007-qq-bot-solves-its-own-pow.md)）。

## 另外两处被这个问题连带暴露的缺陷

1. **每轮对话写了两条日志。** `handleChatCompletion` 内部写一条，QQ webhook 又写一条。审计台看起来像"每条消息都被推送了两次"。已加 `skipLog` 让 webhook 独占记录职责。

2. **错误文案会退化。** 模型返回空内容时，`payload.error?.message ?? \`HTTP ${res.status}\`` 落到后半段，记录成 `HTTP 200` —— 一条毫无诊断价值的错误。现在区分"上游报错""模型返回空""重试后仍为空"三种情况。

**并且加了空回复重试**：拿到空内容时换一个新解重试一次。根因已经堵住，这个重试是给上游偶发空回复兜底的。

## 为什么要单独记这一条

因为它是**"看起来完全正确"的优化的典型**：缓存是标准做法，300 秒有效期也是真的，复用看起来毫无风险。危险不在推理过程，而在**一个未被验证的前提**（解可以被复用），而它的违反方式不报错。

这和本项目之前那几个 PoW 实现缺陷是同一类：**产出貌似合理的结果，只有独立验证才能发现。** 这里的"独立验证"就是那个把同一个解连着发两次的对照实验 —— 两行输出，一次就定案。

## 后果

- `obtainPowHeader` 无状态。`/pow/warm` 与缓存相关的展示**保留但明确标注为不可用**（`usable: false`），因为留着它们比删掉更能说明"这里曾经错在哪"。
- 判断"一次性的东西"是否真的可复用，**必须实测**，不能从"它有有效期"推断。
- 空回复现在会**自动重试一次**，并在重试后仍为空时给出明确措辞。

## 已考虑并否决

- **保留缓存，但用后立即失效**：需要在上游返回后才删除，而"复用被接受但答案为空"意味着**本地无法判断解是否已被消耗**——只有上游知道。任何基于本地状态的失效逻辑都是猜。
- **给解加使用计数**：同上，无法可靠地在本地追踪上游的消耗状态。
- **检测空回复后重试（仅此而已）**：治标。缓存复用会让每条消息都空一次再重试一次，延迟翻倍而根因仍在。
