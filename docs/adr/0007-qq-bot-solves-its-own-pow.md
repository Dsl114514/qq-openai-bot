# QQ bot 自己求解算力挑战，不再需要预热缓存

这是一个**被实测推翻的设计假设**，而且推翻的方向很值得记下来：原来的方案不是"不够快"，而是**为一个不存在的限制做了大量工作，并因此拒绝了本该能回答的请求**。

## 原来的假设

`wasm_solve` 没有起始 nonce 参数（见 [ADR-0001](0001-pow-in-js-not-wasm.md)），所以在 TypeScript 里重写 Keccak-23 并按区间分块。本机实测 **19.8 µs/hash**，于是难度 144,000 的一次完整求解约需 **350 ms**。

对照免费版每次调用 **10 ms CPU**，结论是：一次调用**绝对算不完**，需要上百次调用。而 QQ 事件处理只有 30 秒 `waitUntil` 预算，走不完那个循环。

于是做了这些：

- 一个 `/pow/warm` 端点，把外部算好的解存进 D1；
- 一个 `scripts/chat.mjs --warm`，让使用者手动预热；
- webhook 里检查缓存，没有就回复**"算力挑战未就绪，请先预热"**。

## 实测结果

部署后用 `scripts/probe-ceiling.mjs` 二分探测真实 CPU 天花板：

```
count=106250   HTTP 200   1302 ms
count=148437   HTTP 200   1455 ms   ← 最大成功
count=162500   killed                ← 被杀
```

**天花板约 150,000 次哈希**，即约 **67 ns/hash** —— 比本机快约 **300 倍**。

而难度只有 **144,000**。也就是说：**一整次挑战的搜索空间，能塞进一次调用。** 实测端到端 2–3 个区间、1.1–1.7 秒。

原来估算的"上百次调用"差了**两个数量级**。

## 后果

- QQ bot **自己求解**，不再需要 `/pow/warm`、不再需要手动预热。缓存仍然保留，但只是**加速**（一次求解 300 秒有效期内复用），不是**前提**。
- 原来的失败模式很糟：缓存过期时 bot 回复"未就绪"，而那份工作其实**完全负担得起**。这是把一个不存在的限制变成了对使用者的拒绝服务。
- `SOLVE_CHUNK` 设成 **200,000**，**大于**难度。理由是 `solveRange` 会按区间大小分配缓冲区，分块反而增加总分配量 —— 分块在这里是反常的。循环保留只是为了让将来难度变大的挑战仍能工作；今天的第一轮就结束了。
- `--warm` 仍然存在（对 `scripts/chat.mjs` 的调用方有用），但**不再是使用 QQ bot 的前提**，`/admin/status` 也已改掉那句"请运行 --warm 预热"。

## 一个必须说明的限制

**这个方案不能抵御 CPU 被杀。** 调用超限时运行时**直接终止**它 —— 没有异常可捕获、没有部分结果可挽救。围绕求解写 `try/catch` 对真正的威胁毫无用处，声称有用比直说更糟。

真正让设计成立的是**测量数字本身**：天花板 15 万 > 难度 14.4 万，留有余量。残留风险是**冷 isolate**（实测同样工作量的墙钟在冷热之间差 4 倍），此时那一条回复会丢失，下一条消息重新求解。这在审计日志里表现为**一条没有回复的记录** —— 这是诚实的失败方式，比一个静默的错误答案好得多。

## 已考虑并否决

- **继续依赖预热缓存作为前提**：它把一个可负担的操作变成了使用者必须记住的手动步骤，失败时还伪装成"系统未就绪"。
- **在 `waitUntil` 里分多次调用求解**：`waitUntil` 预算只有 30 秒，而分块在同一 isolate 内无法跨越调用边界 —— 这是最初就否决分块方案的同一个约束。
- **用 `ctx.waitUntil` 起一个 Durable Object 来慢慢算**：DO 的 alarm 同样只有 10 ms CPU，没有解决问题，只是把问题搬到别处。
