# QQ 机器人走官方 Agent 通道的 AppID/AppSecret，而不是第三方协议或自建审核流程

QQ 侧有两条路，性质完全不同：

1. **官方开放平台 Agent 通道**（`q.qq.com/qqbot`）：在网页上点"创建机器人"**立刻**拿到 `AppID` + `AppSecret`，**不需要主体认证、不需要提审**。事件通过 **HTTPS webhook** 投递（端口限 80/443/8080/8443，回调地址只需是 HTTPS，**官方文档没有任何 ICP 备案或域名后缀要求**）。签名用 **Ed25519**，而 Workers 的 WebCrypto **原生支持 Ed25519 verify**，不需要引库。
2. **NapCat / Lagrange / OneBot**：能力更强（真实 QQ 号的真实群），但**必须在某台机器上常驻一个已登录的 QQ 客户端**，且 Worker 只能当它的 webhook 目标而不能承载它。

选 1，因为约束是"全部部署在 Cloudflare 免费版、且不接受任何外部常驻机器"。选 2 会同时破坏这两条。

## 一个被证伪的顾虑

社区（LangBot 集成文档、Koishi 论坛版主）普遍流传"QQ 官方禁止接入 AIGC 功能"。**我抓取了官方运营规范全文核对：没有任何 AIGC / 生成式 AI / 大模型 的禁令条款**，该页标注的上次更新是 2023-11-09。而且官方一直在主动推 Agent 接入（OpenClaw / Hermes / Workbuddy / QClaw 都是首屏推荐），说明 AIGC 本身不是被禁的对象。

**但同一份规范里有一条同样致命、且白纸黑字的条款**（5.1 内容安全）：机器人**涉及未设置过滤违法、违规不当信息内容机制**的，「一经发现将根据违规程度对该 QQ 机器人帐号封禁搜索、添加能力，直至下架处理」。裸接大模型、输出不过滤，正是这条描述的形态。

## 后果

- 一旦要**公开发布**（而非只跑沙箱），内容安全过滤就不是可选项。这影响通道适配器的接口形状：**过滤必须是一个能在发送前拦截的钩子**，而不是散布在各处的检查。
- 运营规范 5.10 要求在终止服务后**删除用户数据**。这直接约束调用记录的保留策略——来自 QQ 来源的记录不能承诺永久留存。
- 通道以适配器形式实现，官方 webhook 是 v1 唯一实现，OneBot 系作为第二个实现预留。切换通道不应触碰服务层。
