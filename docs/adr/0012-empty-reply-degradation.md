# 空回复的三级降级：丢掉父指针 → 换新会话，且每次重试都要新解

## 现象

群里 @机器人 报：

```
出错了：the model returned an empty reply twice, even with a fresh challenge
```

这句错误信息本身**就是诊断线索**：它说"换过新挑战了还是空的"。既然换挑战没用，那**坏的就不是挑战**。

## 第一次修复错在哪

原来的"重试"是这样的：换一个新挑战，然后**重发完全相同的请求** —— 包括同一个 `parent_message_id`。

如果坏的正是那个父指针（上游已经不再接受它），那么重试**注定失败**，而且失败方式很具体：上游返回 **HTTP 200 加空内容**，`completion_tokens: 1` —— 不是错误码。所以"换了新挑战还是空"就成了必然。

**换了一个坏掉的东西，没换真正坏的那个。**

## 正确的降级顺序

空回复有多种成因，所以需要按顺序试三种，每种的代价递增：

| 步骤 | 请求内容 | 对应成因 |
|---|---|---|
| 1 | 沿用会话 + 父指针 | 正常路径 |
| 2 | 沿用会话，**去掉父指针** | 父指针失效 |
| 3 | **全新会话**（两个 id 都不带）+ **清掉存储的坏会话** | 会话本身失效 |

**第 3 步的"清理"才是修复，而不是重试。** 不做清理的话，坏会话行会一直留着，之后**每条消息都撞同一个坏指针** —— 表现为"机器人突然不说话了"，而日志里全是 200。

## 第二个错误：重试复用了同一个 PoW 解

修好降级链之后，实测仍然失败，而且**只用了 1434ms** —— 如果真跑了三次上游调用（每次约 1.3 秒），不该这么快。

原因是**PoW 解是一次性的**（见 [ADR-0008](0008-pow-solution-is-single-use.md)）：复用同一个解返回 200 加空内容。调用方给的那一个 header 只能覆盖**一次**调用，而降级链最多需要**三次**。

于是第 2、3 步**因为跟会话无关的原因失败**，而它们**失败得很快**（没有真实生成），让整条链看起来是坏的，实际上它什么都没做。

**修法**：每次尝试都取自己的解。第 1 次仍用调用方给的（不浪费它的求解），后续由 Worker 自己解 —— 它能做到，因为 CPU 天花板约 15 万哈希而难度 14.4 万（见 [ADR-0007](0007-qq-bot-solves-its-own-pow.md)）。

> 值得记下来的是：这个 bug 和第 5 节的"缓存解"是**同一类错误的第二次发作** —— 都是把一个一次性资源当成可复用的。第一次在存储层，这次在调用层。

## 实测验证

`scripts/verify-recovery.mjs` 会往会话存储里塞一个**真正坏的**会话（不存在的 UUID + 假父指针），然后发消息：

```
seed: 全零 UUID + parent 999999
第一条消息  → "恢复成功"   ✅（修复前是空的）
坏会话已清除               ✅
第二条消息  → "第二次"     ✅
```

**关键是第一条就救回来了** —— 这才是真正的修复；只让"下一条"能用是把问题缩小，不是解决。

## 同样修在 `/v1` 上

第一版只在 QQ webhook 里加了降级，`/v1`（含工作台、所有 API 调用方）**完全没有** —— 那里遇到坏会话会**永远返回空内容**，每条响应都是 200，没有任何提示。

**同一个缺陷不能只在发现它的那条路径上修。** 现在两条路径共用同一个 `completeWithDegradation`，区别只在于取解的方式。

## 已考虑并否决

- **无限重试**：每一级都有代价（额外一次上游调用），而"三次都空"通常意味着上游本身在返回空，再试只是烧调用次数。
- **检测到空回复就自动清会话了事**：能"修好"表现，但会把一个可能只是父指针失效的会话整个丢掉 —— 用户白丢上下文。分级的意义就是**先付出最小的代价**。
- **把解也放进降级链缓存**：解本来就是一次性的，缓存一个只会制造 ADR-0008 那个 bug。重试必须取新解。
