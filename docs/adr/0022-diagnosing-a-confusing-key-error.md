# 诊断一个"看不懂的 Key 错误"：三次误判和它们各自的原因

一个中转端点报告 `HTTP 429 error code: 1015`，同时提示 `HTTP 403 FreeTierError`。查清它花了几轮，而**每一轮我都先得出了一个错误结论**。记下的是那三个误判，因为它们各自对应一类会重犯的推理错误。

## 误判一：把"限流"当成"永久封锁"

现象：从本机访问该域名一切正常（200/401 都合理），从 Worker 访问**每次都** 429。连续轮询 3 分钟、间隔 20 秒，**9 次全部失败**，再等 60 秒仍然失败。

我当时的结论：Worker 的出口被永久挡了，代码层面无解。

**错在哪**：我把"我观测到的持续时间"当成了"限制的持续时间"。**每一次探测本身都在重置限制窗口** —— 一个"每窗口 N 次、超了冷却 X"的规则，在**持续轮询**下永远不会恢复。所以我的测量方法决定了结果必然是"一直失败"。

正确的做法是：**停手一段时间，只发一个请求**。

## 误判二：一次发 7 个请求去"穷举形态"

为了找出哪种请求形态能被接受，我写了一个诊断接口，**一次尝试 7 种**（换 User-Agent、加 Origin/Referer、无 Key、根路径……）。

结果长这样：

```
1. baseline（只带 authorization） → 200 ✓  156ms
2. + browser User-Agent          → 429    5ms
3. + UA + Accept                 → 429    5ms
...
7. 无任何 header                 → 429    4ms
```

**我差点据此得出"只有 baseline 形态可行"的结论。**

**错在哪**：2–7 的响应时间是 **2–5ms**，而 1 是 **156ms**。5 毫秒是**边缘直接拒绝**，请求根本没到源站 —— 那是**突发限流**，不是形态问题。**是这 7 个请求自己把限制触发了。** 测量行为改变了被测量的对象。

> 一个诊断工具如果一次发多个请求，它就在**制造**它要调查的那个现象。

**修法**：诊断接口改成**每次只发一个形态**，由调用方选择。请求数与普通的探测相同，不再自己打爆限流。同时把**响应时间**作为一等输出 —— "2ms 的边缘拒绝"和"300ms 的源站拒绝"是两件完全不同的事，而状态码看不出这个区别。

## 误判三：把"模型列表能拿到"当成"Key 有效"

`GET /models` 返回 **200，87 个模型**，目标模型名也在列表里 ✓。

我据此认为 Key 没问题，把注意力转向了形态和地区。

**错在哪**：**这个服务的 `/models` 根本不校验 Key。** 它只是公开的模型清单。同一个端点：

```
GET  /models          → 200，87 个模型     ← 任何 Key（甚至没有 Key）都这样
POST /chat/completions → 401 Invalid API key.  ← 这里才真正校验
```

所以"获取模型列表成功"**完全不能证明凭据可用**。而这个区分恰恰是我自己写在界面上的（"探测验证 Key 与 URL；测试对话额外验证模型"）—— 我把那句提示当成了已经成立的事实，而不是需要在这个服务上验证的假设。

**修法**：界面上把两者的含义写死 —— **模型列表成功 ≠ Key 有效**；并保留「测试对话」作为唯一能证明"能对话"的动作。

## 顺带修掉的两个真实缺陷

### 1. `apiKey` 字段被静默忽略

端点列表重构后，保存 Key 只认 `key:<id>`。而**旧的 `apiKey` 字段不再被处理，也没有报错**：

- 返回 `{ok: true, detail: "已保存..."}`
- 数据库里**什么都没写**
- 调用方以为轮换成功，实际用的是旧 Key

这正是本项目反复修的那一类：**说保存成功，什么也没变**。我自己的几个脚本就踩了它 —— 它们用 `apiKey` 提交，一次又一次"成功"地什么都没做。

这解释了用户的一个观察：他确实看到过"Key 不对"。他的直觉方向是对的。

**修法**：
- `apiKey` 作为**第一个端点的别名**继续被接受（旧客户端和脚本不再静默失效）
- 指向不存在端点的 `key:<id>` 现在**返回 400 并说明**，而不是装作成功
- 保存摘要**点名写出了哪个指纹**（`已写入 Key：迁移的端点=a2ed4852`）—— 让人**一眼**看出存进去的是不是自己给的那把

### 2. 诊断端点返回 400，把诊断文字吞掉

探测发现端点不健康时返回 `HTTP 400`，而控制台的通用请求助手把非 2xx 当传输失败抛出 → 屏幕上只剩 `400 (Bad Request)`，**我写的那整段分析被替换成了一个状态码**。

语义上错了：**探测请求成功了，它的结论是端点不通。** 那是响应体里的 `ok: false`，不是畸形请求。

**修法**：诊断类端点**始终返回 200**；客户端也补上读 `detail` 字段（服务端的形状），不只读 `error.message`（OpenAI 的形状）—— 只读后者正是那个裸 `HTTP 400` 的来源。

## 最终结论

用指纹证明 Key **保存正确**（与用户给的一致），然后用**真实补全请求**证明该 Key **对这个服务无效**：

```
mimo-v2.6-flash-free  → 401 Invalid API key.
claude-sonnet-4-5     → 401 Invalid API key.
gpt-5                 → 401 Invalid API key.
gemini-3.5-flash      → 401 Invalid API key.
```

而先前存过的另一把 Key 得到的是 `FreeTierError: OpenCode's free tier can only be used from within OpenCode` —— 那把**是**有效的免费层 Key，但提供方**明确限制它只能在自己的客户端内使用**。那是提供方的许可策略，不是配置问题，也不该被绕过（伪装成他们的客户端可能让用户的账号被封）。

同时确认了架构本身没问题：**Worker 访问该域名完全正常**（`/models` 从 Worker 返回 200）。之前那些 429 是**另一个**域名（`apihub.agnes-ai.com`）的限制。

## 已考虑并否决

- **继续轮询等它恢复**：轮询本身重置窗口，永远等不到。
- **一次尝试所有请求形态**：会触发要调查的那个限流。
- **把 `/models` 200 当作凭据有效的证据**：这个服务上它不校验 Key。
- **伪装成 OpenCode 客户端绕开免费层限制**：那是提供方的明确策略，绕过可能导致用户账号被封。
- **删掉诊断能力**：它回答过"端点到底能不能从 Worker 访问"，所以保留，但改成每次一个请求。
