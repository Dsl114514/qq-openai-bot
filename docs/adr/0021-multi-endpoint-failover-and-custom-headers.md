# 多端点与自定义请求头：让 API 接入经得起单个端点失效

## 为什么一个端点不够

一个只配置一个端点的机器人，**可用性就等于那个端点的可用性**。一次限流、一个额度用尽的 Key、一台短暂宕机的中转，都会让所有消息失败。中转服务彼此也有差异 —— 有的需要额外请求头，有的提供不同的模型集合 —— 所以"用哪个端点"必须是**无需改代码就能改**的部署决策。

因此配置变成**有序列表**：第一个启用的端点优先，只有在前面的端点以"换一个可能成功"的方式失败时才尝试后面的。

## 故障转移对什么有效，对什么无效

这个分类是**刻意的，不是"什么都试一遍"**：

| 失败 | 是否换端点 | 为什么 |
|---|---|---|
| 401 / 403 | ✅ | 该端点不接受这个 Key |
| 429 | ✅ | 限流 —— **这正是故障转移存在的理由** |
| 5xx / 超时 / 连接失败 | ✅ | 该端点暂时不可用 |
| **400 / 422** | ❌ | **请求本身有问题，每个端点都会一样地拒绝** |

把畸形的请求对每个端点重放，会烧掉整个列表的额度，并把**一个清晰的错误变成 N 个令人困惑的错误**。

## 三个实测踩到的问题

### 1. 空回答不触发故障转移（这是设计，不是疏漏）

一个 200 但没有内容的回答，是"一个能工作的端点给了一个没有内容的回复"—— 那是一个**真实的（虽然没用的）回答**。换端点会静默替换成**另一个模型**的意见，而没人能分辨是哪个模型在说话。

只有彻底失败才继续往下走。

### 2. 已经流出的部分文本要保留，且不能再试下一个

部分回答胜过什么都没有，所以**已产生文本就返回它**。同时**必须停止**继续尝试 —— 否则用户会看到两个回答拼接在一起。

这条测试一开始是有竞态的：服务器在写入那一帧后**同步** `destroy()`，会与客户端的读取竞争，那一帧有时根本没送达，于是测试报"空的部分回答"—— 那是**另一个代码路径**，测不到想测的东西。加一个延迟后才稳定。

### 3. 诊断端点返回 400，把诊断文字吞掉了

你实际遇到的：点"测试"看到 `POST .../provider/probe 400 (Bad Request)`，**屏幕上没有任何有用的信息**。

原因：探测在发现端点不健康时返回 HTTP 400，而控制台的通用请求助手把任何非 2xx 当传输失败抛出，于是我精心写的那段"是 Key 还是 URL 还是地区"的诊断文字被替换成了一个状态码。

**语义上这是错的**：

> 探测**请求**成功了。它的**结论**是端点不通 —— 那是响应体里的 `ok: false`，不是畸形的请求。HTTP 400 的意思是"你的请求有问题"，而操作者的请求完全正常。

现在诊断类端点**始终返回 200**，用 `ok` 字段表达结论。同时客户端也补了一层：错误消息会读 `detail` 字段（服务端的形状），而不只读 `error.message`（OpenAI 的形状）—— 只读后者正是那个裸 "HTTP 400" 的来源。

## 模型名：从"打错了看不出来"到自动补全

**实测**：模型名被输入成 `d`，而机器人的唯一症状是**"模型返回了空回复"** —— 那读起来像服务商在闹脾气，不像一个拼写错误。

两个改进：

1. **「测试对话」按钮** —— 发一条真实的一 token 补全。它验证的是**模型能不能回答**，而不只是 Key 能不能用。探测能证明 Key 被接受、URL 解析正确，但一个有权限的 Key + 正确的 URL 仍然可以指向一个该服务不提供的模型名。
   - 用的是**输入框里当前的值**，不是已保存的值 —— 所以"试试这个模型名"是保存前的安全操作。
2. **`<datalist>` 自动补全** —— 用探测拿到的真实模型列表做补全，同时**保留自由输入**。用 `<select>` 会让"服务提供但未在列表里的模型"变得无法选择。

## Key 的存放：按端点分开，且永远只返回指纹

```
provider:endpoints   -> [{ id, label, baseUrl, model, enabled, headers }]   （非机密）
provider:key:<id>    -> 每个端点各自的 Key                                    （机密）
```

Key 不在端点对象里。这让"永远不把 Key 序列化进响应"成为**存储布局的属性**，而不是一条需要人记住的规则 —— 任何读取端点列表的代码都不可能带上 Key，因为列表里没有 Key。

返回的是 SHA-256 前 8 位指纹加来源标签。不是为了好看：有两把 Key 的人需要知道装的是哪一把，而唯一安全的回答方式是哈希。实测确认响应里没有 `apiKey` 字段。

### 旧配置自动迁移

早先的版本存一行 `provider:config` 和一行 `provider:apiKey`。只读新的键会让一个配置好的部署**静默退回默认值** —— 丢掉 URL、模型，并且看起来像从未配置过。所以旧行被读一次、折进一个端点、Key 复制到新的按端点位置。**旧行保留**，这样回滚仍然找得到。实测：迁移后端点的 Key 指纹与迁移前一致。

## 自定义请求头

`Name: value` 每行一个。这在实践中是**必需**的，不是锦上添花：一些中转要求 `HTTP-Referer`/`X-Title` 配对（OpenRouter），一些按特定 `User-Agent` 放行，一些要组织 id。没有这个字段，用它们的唯一办法就是改代码。

操作者的自定义头**排在最前**，这样标准头不会被控制台里的笔误破坏 —— 一个打错的 `content-type` 会让每个请求都以看起来像服务商故障的方式失败。

**Key 安全性**：自定义头虽然存在非机密的那一行里（会被返回给浏览器），但把 Key 放在自定义头里的做法通过"按端点的 `key` 字段"来满足，那个字段只返回指纹。UI 明确引导用那个字段。

## 已考虑并否决

- **把单端点也当成一个列表特例**：那正是现在做的 —— 一层抽象，不是两条代码路径。
- **`<select>` 选模型**：会让"服务提供但未在列表里的模型"无法选择。
- **429 时先重试同一端点再换**：会把每个失败端点的延迟翻倍，而换一个端点更可能成功。
- **对 400 也换端点**：烧额度，并把一个错误变成一串错误。
- **诊断失败返回非 2xx**：见上 —— 会把诊断文字换成状态码。
- **把 Key 存在端点对象里**：任何序列化端点的代码都会带上它。
