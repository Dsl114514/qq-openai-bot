# 群标识必须从下拉里选，不能让人手填

## 现象

发牢骚功能配置好了，**从来没有触发过**，而且**没有任何报错**。

查证：

```
配置的群标识 : AC4FBFFF8A2C43F360F6A5B3D06DCB81:B0780D7BE440143E5A2D23D7C7B99E72
真实的群     : AC4FBFFF8A2C43F360F6A5B3D06DCB81
调度状态行   : 不存在（从未被检查过）
发送记录     : 无（从未尝试过）
```

## 根因

**界面让人从会话列表里复制"标识符"，而那里显示的是内部会话 key，不是 `group_openid`。**

会话 key 的格式是 `group:<group_openid>:<member_openid>` —— 它**包含**群 id，但多带了冒号和成员 id。而发牢骚的调度是**用事件里的 `group_openid` 去查配置**：

```js
const groupForCheck = str(event.d?.group_openid);   // AC4FBFFF...（纯净的）
await maybeInterject(env, groupForCheck);           // 用这个去查配置
```

配置存在 `interject_config:AC4FBFFF...:B0780D...` 下，而查询用的是 `interject_config:AC4FBFFF...` —— **永远匹配不上**。所以：

- 配置保存成功（表单不校验）
- 界面显示"已启用"
- **永远不会触发，且不产生任何错误**

这是最难发现的一类失败：**看起来配置好了，什么也没发生，而且没有任何地方说为什么。**

## 为什么值得单独记

因为它暴露的不是一个拼写错误，而是**一个界面设计缺陷**：

> 我把内部标识符展示出来，并让用户把它复制到另一个输入框里。这两个值看起来都是"那个群的长字符串"，而它们并不相同。

用户没有做错任何事 —— 他复制了界面上唯一能看到的群标识。**一个要求人手工搬运不透明标识符的界面，迟早会搬错，而且错了看不出来。**

## 修法：让人从已知的群里选

不是"把提示文字写得更清楚"，而是**取消手填**：

1. **`knownGroups()`** 从**真实事件**里提取群 id —— 只有确实到达过事件的群才会出现在列表里；
2. 表单变成**下拉选择**，并尽可能显示群名（调 `/v2/groups/{id}/info`，失败就退回显示 id 前缀）；
3. **保存时校验**：如果提交的 id 从未出现在任何事件里，**直接拒绝**并说明原因（还会提示"这看起来像内部会话标识"）；
4. 已存在的错误配置在列表里标红 **无效**，并解释为什么。

第 3 条是关键：它把**静默的永久失败**变成了**可见的即时拒绝**。

## 实测

```
下拉框         → 存在，含真实群，显示群名「都市的异想体」
保存错误值     → 被拒：「它看起来像内部会话标识（形如 group:群:成员），请从下拉里选择」
保存正确值     → 已保存：每天 2 次，固定 21:30
立刻发送       → 已发送：「冒泡」   ← 真的发到群里了
无效配置标记   → 显示「无效」徽章
```

## 后果

- **凡是要引用外部标识符的地方，都应该让人从已发现的集合里选**，而不是手填。手填只在标识符可验证时才是可接受的。
- 校验必须在**写入时**做。事后发现"这个 id 从没出现过"需要人去比对，而写入时拒绝是零成本的。
- 顺带修的：**手动发送（「立刻发一条」）之前不写 `call_log`**，所以"测试成功了吗"只能去群里看 —— 而这正是审计台存在的意义。现在它与定时发送记在同一处。

## 已考虑并否决

- **把提示文字写得更清楚**（"请填 group_openid，不是会话标识"）：用户仍然只能看到界面上给的那一个字符串，提示文字不会让搬运变得可靠。
- **自动从会话 key 里截取群 id**：会让 `group:A:B` 和 `group:A:C` 都变成 `group:A` —— 看起来方便，但它掩盖了"这两个是不同的会话"这个事实，而且截取规则一旦猜错就是另一个静默失败。
- **只在后台警告、不拒绝保存**：警告会被忽略，而错误配置一旦存下就会永久静默失效。
