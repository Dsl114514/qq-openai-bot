# 鉴权漏洞：/pow/* 完全公开，且 workbench 身份靠可伪造的请求头判定

这是部署到真实 Cloudflare 账号后**实测发现的两个漏洞**，不是代码审查的推断。两者都已修复，并且处理方式被固定在 `scripts/verify.mjs` 里，防止复发。

## 漏洞一：`/pow/*` 系列端点没有任何鉴权

实测（`https://<worker>/...`，**不带任何凭据**）：

| 端点 | 返回 |
|---|---|
| `GET /pow/status` | `200` —— 泄露会话令牌指纹 |
| `POST /pow/chunk` | `200` —— 任何人都能烧配额 |
| `POST /pow/calibrate` | `200` —— 同上 |
| `POST /pow/challenge` | `200` —— **用持有者的 DeepSeek 会话去请求上游** |

危害不是理论上的：

- `/pow/challenge` 会**消耗持有者的 DeepSeek 账号**去打上游接口。
- `/pow/chunk` 会**烧掉持有者的每日 10 万次请求配额和每次调用 10 ms 的 CPU 预算**。这不是抽象的配额问题——本项目整个 PoW 方案之所以成立，就是靠把 15 万次哈希塞进单次调用的 CPU 预算里；别人可以让这些调用全部落在你的账单上。
- 更糟的是它不只会耗尽配额：**配额耗尽的表现是"服务开始失败"，而这和上游出问题完全无法区分。**

修复方式是**一个 `app.use('/pow/*')` 中间件**，而不是在每个处理函数里各加一次检查。原因是：漏掉一个端点的失败模式是**静默的**（端点只是继续对陌生人可用），而中间件让"/pow 下新增的路由默认受保护"成为结构性事实，而不是纪律要求。

## 漏洞二：workbench 身份由请求头判定，而请求头可以伪造

原本 `/v1/*` 信任 `x-origin: workbench` 作为"来自管理后台"的证明，从而免除访问密钥。实测：

```
-H 'x-origin: workbench'  /v1/chat/completions  ->  428   （无密钥直达上游）
-H 'x-origin: workbench'  /v1/models            ->  200
```

**任何人都能发这个头。** 一个由调用方自己声明、且无法被验证的身份标签，不是凭据 —— 它是一句自述。

修复：workbench **不再靠任何自述**，改为使用它本来就已经持有的凭据。`/admin/*` 在 HTTP Basic 认证之后，浏览器的 fetch 带上 `credentials: 'same-origin'` 即可复用同一个管理密码；服务端**真正校验**它，而不是相信一个标记。

## 为什么这两个漏洞值得单独记录

因为它们的共同形状是"**看起来是安全的**"：路由文件里有鉴权代码，`/admin` 也确实做了检查，测试也全绿。漏洞在于**检查没有覆盖到的地方**，而覆盖缺口不会以任何方式显形 —— 端点只是安静地对所有人开放。

这也说明了一件事：**"部署后的真实探测"能发现代码审查发现不了的东西。** 两个漏洞都是通过实际发送无凭据请求发现的，而不是通过阅读代码。

## 后果

- `scripts/verify.mjs` 现在对**每一个**端点断言"无凭据时必须 401"，包括伪造的 `x-origin` 头。这两条断言的存在意义就是：如果将来有人重新引入这类信任，验证会立刻失败。
- 访问密钥与管理密码现在是 `/pow/*` 的两种合法凭据；`/v1/*` 同理。两者都经过常量时间比较（见 `safeEqual`）。
- 已考虑并否决：**用 Cloudflare Access 保护 `/pow/*`**。它更强，但要求一个自定义域上的 Access 应用，而 `qq.hacknet.de5.net` 虽可用，却会让 `scripts/chat.mjs` 这类外部驱动必须处理 Access 的 service token —— 对一个免费版个人工具来说，复杂度换来的边际安全性不成比例。管理员密码 + 常量时间比较已经覆盖了实际威胁（陌生人不该用你的配额）。
