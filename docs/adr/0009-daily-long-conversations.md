# 长会话需要「会话 id + 上一条消息 id」两者，且不设定时任务

需求是 **QQ 用户每人每天一个长会话**：当天发的所有消息都在同一个线程里，跨天自动重置。

看着简单，但有一个**靠读代码无法确定的前提**：completion 请求体同时带 `chat_session_id` 和 `parent_message_id`，上下文到底靠哪个维持？猜错的代价是 bot"自信地失忆"——那看起来像模型不行，不像集成错了。

## 实测（不是推断）

`scripts/test-session-continuity.mjs`：第一轮说一个代号，第二轮问回来，三种连接方式对照：

| 方式 | 结果 |
|---|---|
| A. 同一会话 + `parent_message_id` | **REMEMBERS** ✅ |
| B. 同一会话 + `parent_message_id = null` | 失忆 ❌ |
| C. 新会话（对照） | 失忆 ❌ |

**两者缺一不可。** 只存会话 id 是最容易犯的错，因为它在数据库里看起来完全正确。

## 实现要点

- 状态是**每用户一行**（`app_state` 的 `qq_session:<openid>`），存 `{sessionId, lastMessageId, day, updatedAt}`。
- **跨天不用定时任务**：不比较"上次是什么时候"，而是比较存储的 `day` 和当前的 `day`。判断发生在用户写消息时。少一个定时任务就少一个会静默失效的东西。
- 「天」按**用户本地时区**算（默认 `Asia/Shanghai`），不是服务器时区 —— 用户应该在**自己的**零点换会话。时区非法时回退并**记录日志**，而不是静默按 UTC。
- **上游没返回 message id 时保留旧指针**，不清空。清空就等于下一轮失忆（上面实验 B）。
- 上游没返回会话 id 时**不写入半条记录** —— 没有会话 id 的会话无法延续，写进去只会制造一个坏状态。

## 给 `/v1` 调用方的 `session_key`

QQ bot 内部一直有长会话，但 `/v1` 调用方没有 —— 他们必须自己保存**两个** id，漏掉任何一个就静默丢上下文。

新增 `session_key` 字段后，调用方只需要记住自己的标识符，Worker 负责存和传。实测验证：同一个 key 记得住，不同的 key 互相隔离。

> 这是 OpenAI schema 之外的扩展字段，命名上刻意做得显眼（`session_key`），不与标准字段混淆。

## 用户可控

`/reset`（也接受 `/new`、`/重置`、`/清空`）立刻开新会话，不必等到明天。命令在 webhook 里拦截，**不会送给模型** —— 否则"重置"这两个字会被当成 prompt。

## 隐私

会话行把 `openid` 和一条活着的对话线程关联起来，属于用户数据，而腾讯运营规范要求服务终止时能删除用户数据。所以：

- 后台 `/admin/qq` 有按「N 天未活动」清理的入口；
- `purgeSessions` 支持传截止时间或清空全部；
- 无法解析的行在清理时一并删除。

## 已考虑并否决

- **存完整历史、每轮重放**：需要自己实现上下文窗口管理，而且会把用户的历史消息反复发给上游 —— 上游的会话机制本来就是干这个的。
- **用定时任务（Cron）在每天零点批量重置**：多一个会静默失效的组件，而按需比较 `day` 的效果完全相同。Cloudflare 免费版的 Cron 也只有 10 ms CPU，做批量清理本来就不合适。
- **只存会话 id**：实测会失忆（实验 B）。这正是本 ADR 存在的原因。
- **按 UTC 换天**：用户在北京时间早上 8 点换会话，而不是自己的零点。
