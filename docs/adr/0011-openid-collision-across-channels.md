# 群聊和单聊的 openid 完全相同，会话必须按渠道隔离

## 现象

群里 @机器人：

```
出错了：the model returned an empty reply twice, even with a fresh challenge
```

而单聊同一时间也开始返回空。

## 根因

**QQ 对同一个人返回的单聊 `user_openid` 和群聊 `member_openid` 是完全相同的字符串。** 实测两条真实事件：

```
C2C   author.user_openid    = B0780D7BE440143E5A2D23D7C7B99E72
group author.member_openid  = B0780D7BE440143E5A2D23D7C7B99E72   ← 一模一样
```

长会话按 openid 存，于是**群聊和单聊被合并成同一条会话记录**。

## 为什么表现为"空回复"，而不是报错

会话状态里存着 `parent_message_id`，代表"这个线程的最后一条消息"。合并之后，两个渠道**共用同一个父指针**：

```
id=92  单聊 "你是谁"      → reply msgId "2"   正常
id=93  单聊 "你是猫娘…"   → reply msgId "4"   正常
id=94  单聊 "扮演猫娘"    → reply msgId "6"   正常
id=99  群聊 "hi"          → 空 (ctok=1)   ← 用了 parent "6"
id=100 单聊 "hi"          → 空 (ctok=1)   ← 也用了 parent "6"
```

上游对一个**已被消费的父指针**返回 HTTP 200 加空内容，`completion_tokens` 是 1 —— 不是错误码。

**而重试救不了**：重试重发的是**同一个请求**，包括那个坏掉的父指针。这正是"twice, even with a fresh challenge"的来历 —— 换新挑战没用，因为坏的从来不是挑战。

## 修法

会话 key 从 `<openid>` 改成带渠道前缀：

```
c2c:<openid>                    单聊
group:<group_openid>:<openid>   群聊（每个群独立线程）
```

群 id 也进 key，所以同一个人在两个群里也是两条独立线程 —— 这才符合直觉。

## 旧记录的处理

旧 key 格式的记录**不是"没用了"，而是"有歧义"**：它们可能混着两边的内容。所以：

- `isLegacySessionKey()` 识别它们；
- **绝不继承**为任何一边的上下文 —— 继承一个可能属于另一边的上下文，比失忆更糟；
- 后台标注为 `旧格式 / 不可用`，并提供一键清理；
- `current: false`，所以它们不会被当作可延续的线程。

代价是这些用户损失一轮上下文。这是**有意选择的代价**：宁可失忆，不可串话。

## 为什么会发生

这是我在**加了长会话之后才引入**的缺陷。原来的代码每次都是新会话，没有共享状态可撞；引入"每人一条线程"时，我按"发送者"做 key，而**"发送者"在 QQ 的两个渠道里恰好是同一个字符串**。

值得记下来的教训是：**身份标识的唯一性要按用途验证，不能按名字推断。** `user_openid` 和 `member_openid` 名字不同、语义不同（一个标识"谁"，一个标识"谁在这个群里"），但值相同 —— 而我假设了名字不同就意味着值不同。

## 已考虑并否决

- **按"是否带 group_openid"区分**：等价于现在的做法，但依赖字段存在性而非显式前缀，日后加渠道时容易漏。
- **上游返回空就重试更多次**：重试重发同一个父指针，永远不会成功。这是本 ADR 存在的直接原因。
- **检测到空回复就自动清空会话重试**：能"修好"表现，但会把群聊和单聊永久绑在一起继续互相干扰 —— 治标，而且掩盖了真正的结构问题。
