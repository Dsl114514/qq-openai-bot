# 沙箱与正式是两台主机，`QQ_SANDBOX` 必须匹配所回复的资源

## 现象

群里 @机器人，模型答得好好的，回复却发不出去：

```
reply not delivered: passive HTTP 400 (11292: 沙箱环境不能访问此资源),
                     proactive HTTP 400 (11292: 沙箱环境不能访问此资源)
```

## 诊断

`11292` 只说明"**沙箱**主机不认识这个资源"，但它**不说明资源属于哪一边** —— "这是个正式群"和"这个群没登记成沙箱群"会给出完全相同的报错，而两者的修法**互相排斥**。所以不能靠推断，只能分别问两台主机。

`scripts/probe-group.mjs` 就是干这个的：

```
[sandbox   ] group-info -> HTTP 400
[production] group-info -> HTTP 200
   {"group_name":"都市的异想体的闲聊群⁧~喵⁧[国庆快乐]","group_member_num":39}
```

**结论明确：这是正式群。** 之前 `QQ_SANDBOX = "true"`，所以每次发送必然失败。

## 修法

`QQ_SANDBOX = "false"`，重新部署。实测确认：

```
[production] proactive-send -> HTTP 200
   {"id":"ROBOT1.0_9CHbXDWMQL5bFQKGv1aU19-…","timestamp":"2026-10-07T15:55:33+08:00"}
```

有意思的是**同一次探测里沙箱主机仍然是 400** —— 两个方向同时被验证，这不是巧合。

## 为什么要加容错而不是只改配置

配置改对了，但这个错误的**结构**值得防一手：它会在配置与资源不匹配时**丢弃一整轮已经算完的回复** —— 模型调用、PoW 求解全都白做，用户什么都收不到。

所以 `sendQQMessageResilient` 遇到 `11292` 时**自动改到另一台主机重试一次**。配错因此从"丢回复"降级为"慢一点"。

这是**安全网，不是正路**。`WRONG_ENVIRONMENT_CODES` 目前**只有 11292**，并且有测试钉住这个集合 —— 每加一个码都意味着每次失败多发一次请求，值得显式察觉。`11255`（收件人不存在）和 `22009`（配额）明确**不在**集合里：它们不是环境问题，换主机重试毫无意义。

## 一个容易搞反的方向

这个设置**不是偏好，是匹配**：

| 设置 | 主机 | 能回复 |
|---|---|---|
| `true` | `sandbox.api.sgroup.qq.com` | 只有沙箱群 / 沙箱账号 |
| `false` | `api.sgroup.qq.com` | 正式群 / 正式用户 |

**正式群在沙箱主机上够不到，反之亦然。** 没有"两个都能用"的选项，所以引入了自定义域名之后仍然要注意：域名是入口，主机是出口，两者无关。

## 已考虑并否决

- **两台都发（广播）**：会给每个用户发两条消息 —— 其中一条来自错误环境，通常是报错而不是内容。不可接受。
- **自动探测并永久切换**：需要对每个新会话判断归属，而判断本身就要发一次请求；缓存判断结果的复杂度远超收益。配置加容错已经够用。
- **把 11255、22009 也加进重试集合**：它们不是环境问题，重试只会让每次失败多一次无用请求。
